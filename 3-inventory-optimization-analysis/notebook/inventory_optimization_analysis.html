E-commerce Inventory Optimization & Reorder Decision Analysis¶

This project analyzes e-commerce transaction data to identify sales performance, inventory health, slow-moving SKUs, and reorder recommendations.

Business Goal: Move beyond basic reporting and create a simple decision-support workflow for inventory planning.

3. Data Cleaning¶

Real-world sales data often includes cancellations, returns, missing product names, invalid prices, and lines that are not products at all. This section cleans the dataset before analysis:

  1. Remove non-product lines: postage, carriage, manual adjustments, fees, samples, and gift vouchers.
  2. Remove order lines cancelled in full within 24 hours (same customer, product, and quantity). These are order-entry mistakes, not real sales: for example, an order for 80,995 paper craft sets was cancelled 12 minutes later.
  3. Keep valid sales only (positive quantity and price) and drop rows without a SKU or product name.

# 2) Order lines cancelled in full within 24 hours (same customer, product, and quantity).
#    These are order-entry mistakes, not real sales.
def remove_same_day_cancellations(df, invoice, customer, product, qty, date, price):
    is_cancel = df[invoice].astype(str).str.startswith("C")
    purchases = df[~is_cancel].dropna(subset=[customer]).reset_index()
    cancels = df[is_cancel].dropna(subset=[customer]).reset_index()
    cancels[qty] = -cancels[qty]
    pairs = purchases.merge(cancels, on=[customer, product, qty], suffixes=("", "_cancel"))
    pairs["gap"] = pairs[date + "_cancel"] - pairs[date]
    pairs = pairs[(pairs["gap"] >= pd.Timedelta(0)) & (pairs["gap"] <= pd.Timedelta(hours=24))]
    # Match each cancellation to its nearest earlier purchase, one to one
    pairs = pairs.sort_values("gap").drop_duplicates("index_cancel").drop_duplicates("index")
    pairs["value"] = pairs[qty] * pairs[price]
    pairs["minutes_to_cancel"] = (pairs["gap"].dt.total_seconds() // 60).astype(int)
    return df.drop(index=pairs["index"]), pairs

4. Product Category Creation¶

Because the dataset does not include clean product categories, this project creates simple rule-based categories from product names. In a real company, this could be replaced with a product master table.

def categorize(desc):

    desc = str(desc).lower()

    # Home decor (largest category in this dataset)
    if any(word in desc for word in [
        "candle", "holder", "lamp", "frame",
        "mirror", "vase", "clock", "heart",
        "flower", "light", "decor", "ornament",
        "door", "picture", "sign", "hanger",
        "shelf", "storage", "box", "drawer"
    ]):
        return "home decor"

    # Kitchen / dining
    elif any(word in desc for word in [
        "kitchen", "tea", "coffee", "mug",
        "cup", "plate", "bowl", "glass",
        "bottle", "jar", "tin", "cutlery",
        "spoon", "fork", "knife", "tray",
        "baking", "pan", "kettle", "teapot",
        "cake"
    ]):
        return "kitchen"

    # Bags
    elif any(word in desc for word in [
        "bag", "purse", "tote",
        "lunch bag", "shopping bag",
        "backpack"
    ]):
        return "bags"

    # Gift / decorative
    elif any(word in desc for word in [
        "gift", "present", "ribbon",
        "card", "wrap", "wrapping",
        "party", "bunting", "decorative"
    ]):
        return "gift/decorative"

    # Seasonal
    elif any(word in desc for word in [
        "christmas", "xmas", "santa",
        "snow", "tree", "easter",
        "halloween", "valentine",
        "seasonal"
    ]):
        return "seasonal"

    # Sets / bundles
    elif any(word in desc for word in [
        "set", "kit", "pack", "bundle"
    ]):
        return "sets"

    # Stationery
    elif any(word in desc for word in [
        "paper", "notebook", "note",
        "stationery", "pen", "pencil",
        "file", "folder", "sticker"
    ]):
        return "stationery"

    else:
        return "other"

7. Inventory Health Analysis¶

The original dataset does not include real on-hand inventory. To demonstrate the decision logic, this project simulates inventory as weeks of supply, so stock scales with each SKU's demand.

Simulation assumption: each SKU holds a random amount of stock with a median of 10 weeks of supply (log-normal, so about 80% of SKUs hold between 4 and 28 weeks). Every SKU holds at least one unit.

Because the counts below depend on this assumption, the value of this section is the decision logic, not the exact numbers. In a real business setting, this step should use actual on-hand inventory from a WMS, ERP, or Shopify inventory export.

In [10]:
# Simulate on-hand inventory as weeks of supply (portfolio demonstration)
rng = np.random.default_rng(42)

# Weeks covered by the transaction data
date_range_days = (df["invoice_date"].max() - df["invoice_date"].min()).days
weeks_in_data = max(date_range_days / 7, 1)

# Planning assumptions
lead_time_weeks = 4
safety_stock_weeks = 2
reorder_point_weeks = lead_time_weeks + safety_stock_weeks   # reorder when coverage drops below 6 weeks
overstock_weeks = 26                                         # more than ~6 months of supply = overstock

inventory = sku_sales.copy()
inventory["estimated_weekly_demand"] = inventory["units_sold"] / weeks_in_data

# Stock scales with demand: median 10 weeks of supply, log-normal spread, at least 1 unit
weeks_on_hand = rng.lognormal(mean=np.log(10), sigma=0.8, size=len(inventory))
inventory["ending_inventory"] = np.ceil(inventory["estimated_weekly_demand"] * weeks_on_hand).astype(int)
inventory["begin_inventory"] = inventory["units_sold"] + inventory["ending_inventory"]

# Inventory KPIs
inventory["weeks_of_coverage"] = inventory["ending_inventory"] / inventory["estimated_weekly_demand"]
inventory["sell_through_rate"] = inventory["units_sold"] / inventory["begin_inventory"]
inventory["avg_inventory"] = (inventory["begin_inventory"] + inventory["ending_inventory"]) / 2
inventory["inventory_turnover"] = inventory["units_sold"] / inventory["avg_inventory"]

# Inventory status flags (one coverage-based definition each)
inventory["stockout_risk_flag"] = inventory["weeks_of_coverage"] < reorder_point_weeks
inventory["overstock_flag"] = inventory["weeks_of_coverage"] > overstock_weeks

9. Reorder Recommendation Logic¶

This section estimates how much to reorder.

Formula used:

Reorder Point = Weekly Demand × (Lead Time + Safety Stock), with a 4-week lead time and 2 weeks of safety stock. A SKU needs a reorder when it has less than 6 weeks of coverage.

Recommended Reorder Qty = Reorder Point − Ending Inventory (only when positive).

In [13]:
# Reorder point and recommended reorder quantity
inventory["expected_demand_lead_time"] = inventory["estimated_weekly_demand"] * lead_time_weeks
inventory["safety_stock"] = inventory["estimated_weekly_demand"] * safety_stock_weeks
inventory["reorder_point"] = inventory["expected_demand_lead_time"] + inventory["safety_stock"]

inventory["recommended_reorder_qty"] = (
    inventory["reorder_point"] - inventory["ending_inventory"]

10. Inventory Decision Assistant¶

The decision assistant combines stock coverage with ABC classification, so the SKUs that matter most come first.

  • ABC class: A = SKUs that make up the top 80% of revenue, B = the next 15%, C = the last 5%.

Decision Rules

  • Less than 6 weeks of coverage and A-class → Reorder immediately
  • Less than 6 weeks of coverage, B- or C-class → Monitor and reorder soon
  • More than 26 weeks of coverage → Consider promotion or bundle
  • Otherwise → Healthy inventory

# ABC classification by revenue
inventory = inventory.sort_values("revenue", ascending=False).reset_index(drop=True)
inventory["cum_revenue_share"] = inventory["revenue"].cumsum() / inventory["revenue"].sum()
inventory["abc_class"] = np.select(
    [inventory["cum_revenue_share"] <= 0.80, inventory["cum_revenue_share"] <= 0.95],
    ["A", "B"],
    default="C"
)

# Inventory Decision Assistant
def inventory_decision_assistant(row):
    if row["stockout_risk_flag"] and row["abc_class"] == "A":
        return "Reorder immediately"
    elif row["stockout_risk_flag"]:
        return "Monitor and reorder soon"
    elif row["overstock_flag"]:
        return "Consider promotion or bundle"
    else:
        return "Healthy inventory"

11. Business Insights & Action Plan¶

This section summarizes the analysis in a decision-ready format. Instead of stopping at charts, the project explains what actions the business should take.

Key Findings¶

  • A-class SKUs (top 80% of revenue) with less than 6 weeks of coverage need immediate replenishment to avoid lost sales.
  • Lower-value SKUs below the reorder point can be reordered on the normal cycle.
  • Overstocked SKUs (more than 26 weeks of coverage) may benefit from promotions, bundling, or smaller future buys.

Recommended Actions¶

  1. Reorder A-class SKUs with low coverage first.
  2. Run promotions or bundles for overstocked SKUs.
  3. Track weeks of coverage every week, so reorders happen before stockouts.

13. Portfolio Summary¶

This project demonstrates how sales and inventory data can be used to support business decisions. The analysis identifies best sellers, category performance, inventory health, slow-moving products, and reorder opportunities.

Key portfolio takeaway: This is not only a reporting project. It shows how analytics can support inventory planning decisions such as when to reorder, which SKUs need monitoring, and which products may need promotion or bundling.

Beyond this notebook: the reorder and coverage logic above was extended into a live low-code alerting prototype (Zapier + Airtable) that automatically notifies stakeholders when a SKU's coverage drops below threshold — see the Low-Code Alerting Prototype section of the project README for the workflow and screenshots.
